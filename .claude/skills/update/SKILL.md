---
name: update
description: Update this instance from the studio. Replaces studio-owned paths only; never touches anything the manifest lists under client_owned (the person's canon, banks, material, pieces, journal, recipes and the rest).
---

If this studio was built for the person (its repo was made by the new-client job, and `studio-source.md` says `- studio: managed`), updates arrive on their own: each new version is pushed into their repo, and the next session has it. Then don't run `update-studio.sh`. This command only says which version they're on (`studio-source.md`), what the latest change was (the top of `CHANGELOG.md`), and that the next update arrives the same way, with nothing for them to do.

If `studio-source.md` names a template URL, the studio is the person's own: it lives in their GitHub account, nobody else can see inside it, and new versions come only when they run this command. The update fetches the template, which holds the studio's code and nothing of anyone's, and replaces only the studio's own files; their canon, banks, material, pieces and journal never leave their repo and are never touched.

Otherwise, run `bash scripts/update-studio.sh` from this folder (it reads the studio's URL from `studio-source.md`; pass a folder or URL to use another). Then show the person `git diff --stat` and the new version in `studio-source.md`, and tell them in a few lines what changed in the studio (read the top of `CHANGELOG.md`). Say that the save hook commits the update when this reply ends, and that if they want it undone they can say "undo the update". When they say that, find the update's commit as the last one that changed `studio-source.md` (`git log -1 --format=%H -- studio-source.md`), show its message and date in one line so they know it's the right one, run `git revert --no-edit <that commit>`, and tell them which version they're back on. Never `git revert HEAD`: later replies make their own commits, so the update is rarely the last one.

The update replaces only what `studio.manifest.yaml` lists under `studio_owned`. Everything the manifest lists under `client_owned` is theirs and an update never replaces it; read that list rather than this line, since it's the one that's kept current. A studio file they changed is copied to `studio-local-backup/<date>/` before it's replaced, and "bring back my change to <file>" restores it. Inside `.claude/`, only the studio's own settings, hooks, agents and commands are replaced, so anything else they keep there stays.

If the fetch fails with no access: on Cloud, the session can only reach the repos the person let Claude see. Tell them in plain words that the update reads from the template (name its URL from `studio-source.md`), that they need to have accepted the invite to read it if one came by email, and that the template has to be one of the repos Claude can see (when they connect GitHub from the Claude app, GitHub asks which repos; they add it there). Then try again. Never suggest giving anyone access to their own studio to fix this.
